# 给 Codex 的开发入口

项目：ShuttleUp，一个从多人约球到 AA 结清的轻量 Web 应用。

## 直接使用的任务说明

请实现本目录的 `01-PRD.md` 和 `02-SYSTEM-DESIGN.md`。先完整阅读两份文档，再检查现有代码、项目级开发指令和工作区状态。文档确定的业务规则、状态、金额单位、权限、接口和视觉令牌是实现基线；现有早期骨架与其冲突时，按照设计文档的迁移说明修改，不保留两套实现。

按系统设计 M0–M7 顺序进行纵向开发，每阶段同时打通界面、服务、数据和测试。每阶段完成一次可以实际使用的业务切片并提交，再继续下一阶段。目标是完成所有需求，不是在搭出页面骨架、写出接口名称或通过少量单元测试后结束。

技术栈固定为 FastAPI、Vue 3/TypeScript、SQLite、SSE。生产只部署一个应用服务和数据卷；前端构建后由后端同域提供。沿模块划分组织代码，只有课表、场地和 Bot 接入设外部契约，不搭建额外的分布式基础设施。

用户体验按手机优先设计。实现设计令牌、候选卡片、可触屏操作的时间表和个人账单主视图，不套用通用后台模板。每个页面只突出当前主要操作，复杂任务进入对应抽屉或页面。390px 手机端必须能完成全部核心流程。

每个阶段运行相关测试、类型检查和构建，并记录真实结果。阶段记录写入 `docs/IMPLEMENTATION-STATUS.md`，包含完成的需求编号、使用方法、测试结果和外部联调状态。重用固定测试时钟、金额黄金样例与真实 API E2E，不能用前端硬编码模拟已完成的业务。

真实外部接入需要项目使用方指定首个场馆网站，并提供联调时有效的 WakeUp 分享口令。先完成协议、页面和样本测试，拿到输入后完成真实适配；两项真实联调必须单独验收。AstrBot 插件交付全部 PRD 指令、账号与群绑定以及主动通知，不只留下一个空接口。

工作区已有未提交文件时，只操作 ShuttleUp 相关内容，不覆盖其他项目修改。若当前环境不能创建或推送 GitHub 仓库，保留本地完整代码与提交，并准确记录发布状态；不能声称已经推送。

最终交付应包括运行代码、锁文件、迁移、前端构建、AstrBot 插件、真实场馆适配器、测试、容器启动与备份恢复说明，以及逐项验收结果。

## 文件顺序

`01-PRD.md` 解释做什么、业务如何闭环、页面怎样使用、什么结果算完成。

`02-SYSTEM-DESIGN.md` 定义技术实现、数据表、算法、API、事件、Bot 协议、视觉规格、部署和分阶段开发顺序。

文档的 JSON 使用可读别名作为示例实体 ID，实际数据库使用 UUID；示例域名不是已经接入的网站。带 `...` 的 Python 片段表示待实现的接口签名，不是完成代码。

## 完成时要提供的证据

完整四人活动的创建、加入、匹配、订场、到场、分账、付款、收款与归档结果；一次取消后结算与退款结果；两浏览器实时同步；真实 WakeUp 导入与真实场馆查询；实际 AstrBot 指令与主动消息；手机／桌面截图；测试和包体／内存预算的实测结果。
